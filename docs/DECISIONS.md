# privasoc: decision log

Living log of every design decision. Only what is written here is decided.
IDs are stable; superseded decisions are struck through and point to their replacement.
Framing sessions: 2026-09-26 (7 rounds). Previous Codex prototype (`soc-workbench`) is reference only and not reused.

## Goal

| ID | Decision |
|----|----------|
| D0 | Public GitHub portfolio project supporting an application for *Research Engineer, Cybersecurity RL* (Anthropic). Selection criteria: maximise AI-engineering learning, stay simple, stay reproducible by a reviewer. |
| D0b | **Privacy first.** A local LLM is the default. A remote API can be configured, but critical fields are always pseudonymised before any call. |

## Framing

| ID | Topic | Decision |
|----|-------|----------|
| D1 | Context | Homelab first, personal data only. Architecture must not prevent a later production (SOC/MSSP) use. |
| D2 | Input | Raw logs (syslog, files, Windows events, firewall...) that we parse and normalise ourselves. We do not start from pre-built alerts. |
| D3 | AI roles | ~~Initial priorities~~ revised by D19: 1. parser generation, 2. alert triage, 3. Sigma rule writing, 4. natural-language hunting. |
| D4 | Build vs assemble | Hybrid: the normalisation pipeline is ours (learning goal); storage and search reuse existing components. |
| D5 | Definition of done | 3 sources normalised, a detection fires, the AI produces a readable triage, end to end and demonstrable, plus a reproducible evaluation report. |
| D6 | Repository | New clean repository (`privasoc`). The old prototype stays untouched as reference. |

## Technical choices

| ID | Topic | Decision | Rationale |
|----|-------|----------|-----------|
| D7 | Data | Two tracks: **public labelled data** for evaluation and reproducibility; **live homelab data** for the demo, never committed. | Reviewers cannot replay personal logs; public data gives ground truth. |
| D8 | Schema | Elastic Common Schema (ECS). | Sigma mappings exist; LLMs know it well. |
| D9 | Normalisation | Vector + VRL, each parser covered by tests. AI-generated parsers are VRL too. | VRL is sandboxed: a generated parser cannot execute arbitrary code. Vector also handles collection. |
| D10 | Storage and detection | SQLite + Sigma rules compiled to SQL with `pySigma-backend-sqlite`. No OpenSearch. | No heavy infrastructure; SQL also serves NL hunting. |
| D11 | Runtime | Docker Compose, runnable on a laptop with sample data. Live: a Proxmox VM. LLM runs on the GPU workstation, reached over the LAN. | Reproducibility. |
| D12 | LLM providers | One OpenAI-compatible interface: local server by default, any remote API optional. Pseudonymisation is enforced in code for every provider. | Privacy (D0b). |
| D13 | Language | Python (uv, pydantic, FastAPI, Typer, pySigma). | Security and ML ecosystem. |

## Final arbitrations

| ID | Topic | Decision |
|----|-------|----------|
| D32 | Time | Time is not a constraint: ship fast **with every feature**, incrementally. |
| D33 | Learning pseudonymisation | Learn generalisable patterns (key names, regexes) plus a **local-only, git-ignored** value list. Each learned item is **human-approved** with a preview of its effect on the latest logs. |
| D34 | API fallback | Human action by default; automatic when configured (after N local failures) **or when the local model admits its limit or hallucinates** (D38). Every API call is logged (provider, size, number of pseudonymised tokens). |
| D35 | Drain | Drain groups log lines into templates (variable parts become `<*>`). Used for **stratified sampling** and a template-coverage metric. One parser per source. Library: `drain3`. |
| D36 | Local model | Reached through a **configurable URL** (OpenAI-compatible). Any server, any model. Default chosen by a mini-benchmark recorded here. |
| D37 | Licence and publishing | **MIT**. Public from the start; `gitleaks` in pre-commit and CI; `data/` and the vault git-ignored. |
| D38 | Hallucination / limits | (a) Self-report: JSON `status: ok \| cannot_parse \| unsure` + reason; (b) **grounding check**: every extracted value must appear in the raw line or derive from a known deterministic transform (timestamp, case, integer); (c) stagnation: same error class twice in a row. Ungrounded-value rate is an evaluation metric. |
| D39 | Build order | 1. Core (Vector → quarantine → SQLite, regex pseudonymisation, CLI). 2. Generation loop + sandbox + Drain + anti-hallucination + API fallback. 3. Parser evaluation + HTML report. 4. Review UI. 5. Local-LLM pseudonymisation + learning. 6. Sigma + alerts + triage + UI. 7. AI Sigma rules, then NL hunting. 8. Triage evaluation, then Windows and Proxmox collection. |
| D40 | Triage and rules | Structured JSON: verdict (`true_positive \| false_positive \| needs_investigation`), confidence, summary, ATT&CK techniques, investigation steps, suggested SQL. Re-identified only at display time. SigmaHQ rules auto-enabled when their `logsource` matches present data. |
| D41 | Access and secrets | UI on the LAN behind a single access token. Mapping vault in a separate file (mode 600), **encrypted at rest**; HMAC and encryption keys in `.env`. |
| D42 | Parser library | Approved parsers are indexed; the 2-3 nearest (Drain template similarity) are injected as examples. "Learning curve" evaluation: F1 and attempts versus library size. |
| D44 | Structured mode | After two real runs where `qwen3:8b` could not produce valid free-form VRL (syntax from other languages, `+=`, unassigned variables, a single regex for 7 line shapes), a second mode is added and made the default: the model answers with a YAML spec (prefix regex, timestamp, constants, and one regex + ECS mapping per line shape). privasoc validates it in Python (unsupported Rust-regex features, unknown groups, sample lines matching no shape) and compiles it to VRL with a deterministic, tested compiler; lines matching no shape abort and return to quarantine. Same sandbox, ECS and grounding checks afterwards. Free-form VRL stays available (`--mode vrl`), and the evaluation compares both modes: small model with structure versus free-form code. |
| D45 | Target workflow (onboarding a source) | 1. The admin points the device at privasoc (e.g. Pi-hole remote syslog -> privasoc:5514). 2. privasoc detects the **new sender** and lists it as *pending*; its lines are held (not ingested, not sent to any model) until a human **approves the host**. 3. privasoc checks whether the format is **already known**: Vector's built-in parsers (`parse_syslog`, `parse_common_log`, `parse_apache_log`, `parse_nginx_log`, `parse_cef`, `parse_linux_authorization`, key/value...) and already-approved parsers, tried on a sample. 4. **Known** (a built-in parses at least the coverage threshold of the sample): ingestion into ECS through a fixed, tested mapping of that built-in's output; no LLM involved. 5. **Unknown**: lines go to quarantine, the local LLM proposes a parser (structured mode, all checks of D19/D38/I9), a **human approves** it. 6. On approval the rule is deployed to Vector **and the quarantined backlog of that host is re-processed** (backfill), so no line received before approval is lost. |
| D47 | Host health | Every approved host has a health status computed from what privasoc already sees, no agent on the device: **last seen** and **silence** (no line for longer than a threshold derived from the host's usual rate: a silent firewall is a security signal, not only an outage); **volume** (lines per minute vs its own baseline, sudden drops or spikes); **parse rate** (share of lines parsed vs sent to quarantine: a drop means the format drifted, e.g. after a firmware update, and suggests proposing a parser update); **clock skew** (event `@timestamp` vs reception time). Status `ok` / `warning` / `critical` with the reason, shown by `privasoc hosts` and in the UI, exposed on `/health/hosts`, and kept as a history to be usable by alerting (step 6). Thresholds configurable per host. |
| D46 | Positioning | privasoc does not replace Logstash, Vector or vendor integrations: it runs on Vector and uses existing parsers first. The model is the **last resort**, for the long tail no integration covers (in-house apps, rare devices, formats changed by an update), with the quarantine doubling as a drift detector. README states this explicitly. On known formats hand-written parsers are better (reference F1 0.87 vs 0.53), which the evaluation shows. |
| D48 | Review UI (step 4) | Server-rendered pages (FastAPI + Jinja) served by the same process as the API, under `/ui`, with htmx for polling only. **No third-party host**: htmx is vendored and the Content-Security-Policy allows `'self'` only. Access (D41): the API token is entered once; the browser keeps an HttpOnly, SameSite=Strict cookie that is an HMAC of the token (not the token), and every form carries a CSRF token. Pages: dashboard, hosts (approve/reject, health, thresholds), parser review (checks, spec, VRL, attempts, preview, **live run on the latest quarantined lines**, approve/reject), quarantine, events, jobs. Quarantined and held lines are shown **pseudonymised by default**, raw on demand. The CLI and the UI call the same `service` layer, so a decision means the same thing in both. Learned pseudonymisation gets its page with step 5. |
| D49 | Learned pseudonymisation (step 5) | The **local** model reads lines already pseudonymised by the current rules and lists names still in clear (users, machines). privasoc keeps only values really in clear in the lines (grounding) and turns each into the most general rule it can justify: the **key** it follows (`cs1=`), else the **literal value** plus up to three **context regexes** from the plain words on both sides (`\bUser (...) IP\b`). Rules (key, regex, value) are stored **encrypted in the vault**, validated (no generic keys like `msg`, no nested quantifiers, at most one group, no empty match) and change detection only once a **human approves** them, with a preview of their effect on the latest real lines (lines changed, distinct values caught, before/after). A rejected rule is never proposed again. Because this pass sends clear-text lines, it only runs against a model whose address is loopback, private or link-local (checked in code), and never on held lines of unapproved hosts. Before any **remote** API call, the same pass runs on the samples and its findings apply to that call at once (and stay proposals); if the local model is unavailable the remote call is refused unless `PRIVASOC_REMOTE_RESIDUAL_PASS=false`. |
| D50 | Detection rules (step 6) | Sigma, from two sources: a **subset of SigmaHQ** (release `r2026-07-01`: `network/dns`, `network/firewall`, `web/proxy_generic`, `web/webserver_generic`, `linux/builtin`), downloaded at runtime into `data/sigma/` and never committed (Detection Rule License 1.1: author and licence shown with every rule and alert), plus **privasoc rules** in the repository (`src/privasoc/detect/rules/`, MIT) written directly on ECS fields (`logsource.product: privasoc`), including correlations (SSH brute force, port scan, web scanning, DNS tunnelling). A SigmaHQ rule that uses a field privasoc cannot map to ECS, or a feature the engine does not support, is listed as **unsupported with its reason**, never silently dropped. |
| D51 | Sigma engine | Our own Python evaluator on the stored ECS documents (no pySigma): selections (maps, lists of maps, keywords on `event.original`), wildcards, modifiers `contains`, `startswith`, `endswith`, `all`, `re`, `cidr`, `exists`, `gt/gte/lt/lte`, conditions (`and`, `or`, `not`, parentheses, `1 of`, `all of`, `them`), and **Sigma 2 correlation rules** (`event_count`, `value_count`, `group-by`, `timespan`). A per-category table maps Sigma taxonomy fields to ECS (`query` -> `dns.question.name`, `c-uri` -> `url.original`...) and says which events a logsource applies to. Incremental: a cursor on the events table; matches are stored so correlations and alerts point to the exact events. |
| D52 | Alerts | One alerts table for three kinds: **Sigma** (deduplicated per rule, host and correlation group while the alert is open), **host health** (an approved host turning `critical`, D47) and **new sender** waiting for approval (D45, low). Statuses: new, acknowledged, closed as true positive, closed as false positive. The analyst's closing verdict is kept: it is the ground truth for the triage evaluation (step 8). **Outgoing notification** to one generic webhook (JSON, ntfy, Discord or Slack format) above a configurable level; it carries the title, level, count and alert id only, **never event content or host names**. Detection runs in the background of `privasoc serve` and on demand (`privasoc detect run`). |
| D53 | AI triage | Local model by default, remote API only on a human action, always on **pseudonymised** evidence (with the step 5 local pass before any remote call). Input: the rule (title, description, false positives, ATT&CK tags), up to 20 matched events, host health and counts. Output, validated: `verdict` (true_positive, benign, false_positive, needs_more_info), `severity`, `confidence`, `summary`, `reasons` each citing **event ids that must exist in the evidence**, `next_steps`, ATT&CK technique ids (well-formed; those not in the rule's tags are flagged). Anything that fails validation is shown as such, never silently kept. Pseudonyms in the answer are re-identified for display only. The model suggests; the analyst decides. |
| D54 | AI-written Sigma rules (step 7) | Three starting points, all ending in a **proposed** rule a human approves: (1) a request in natural language; (2) an alert closed as **false positive**: the model writes a derived rule with an exclusion, shown with its effect on past alerts (the false positives it would remove and, above all, whether it would hide any alert closed as true positive); approving it disables the original rule; (3) an event or an alert: "a rule that catches this", generalised. The model writes Sigma YAML on ECS fields (`logsource.product: privasoc`); privasoc validates it with the same engine (feedback loop on errors, fields never seen in the events are errors with suggestions), **backtests** it on the stored events (matches, correlation groups that fire) and keeps it only as a proposal. The request and the event samples are pseudonymised before any model sees them; values the model writes are re-identified before the rule is stored, so it works on real data. Rules live in the database, with their request, origin and backtest. |
| D55 | Natural-language hunting | A question ("which sources failed SSH more than 20 times today?") becomes a Sigma rule through the same author path, run over a chosen period with the same engine; results are the matching events or the correlation groups with their counts. **No SQL is written by the model.** A useful hunt can be saved as a rule proposal. |
| D56 | Measuring step 7 | A small bench written by hand: a deterministic synthetic event set (SSH, firewall, DNS, web) with known ground truth, and about 20 requests with the exact events they must return; half **dev** (may guide prompt changes), half **holdout** (never used for tuning). Metrics: share of requests that give a valid rule, precision and recall of the returned events, exact matches, attempts. Local model `qwen3:8b`. |
| D43 | Anonymity | The project is anonymous: no real name, personal handle or real homelab address anywhere (code, tests, docs, licence, git identity). Test data uses placeholders (`jdoe`, `laptop-01`, 192.168.1.0/24). Licence holder: "privasoc contributors". Commits use the GitHub no-reply identity. |

## Implementation notes
Decisions taken while building, same format.

| ID | Topic | Decision |
|----|-------|----------|
| I1 | Collector | Vector 0.55.0. `socket` sources (UDP/TCP 5514) with `codec: bytes` and a `file` inbox: raw lines are never pre-parsed. Source identity = `syslog:<sender>` or `file:<name>`. Delivery to the API through the `http` sink (NDJSON, bearer token, retries). |
| I2 | Pseudonym formats | user `user-xxxxxx`, keyed host `host-xxxxxx`; FQDN label-wise and suffix-consistent, TLD kept; email `uxxxxxx@<fqdn token>`; IPv4 private → 10/8, public → 198.18.0.0/15, /24 kept consistent; IPv6 → 2001:db8::/32, /64 kept consistent; MAC → locally administered `02:...`; SID domain part hashed, RID kept. Collisions resolved by a salt counter in the vault. |
| I3 | Propagation | A value detected once in a line is replaced everywhere in that line (catches free-text mentions of a keyed user). |
| I4 | Leak check | Word-boundary, case-insensitive search of every original in the outgoing text. The CLI refuses to print a line that still leaks. |
| I5 | Vault | SQLite, lookup by HMAC digest, originals encrypted with Fernet, file mode 600. |
| I6 | Sandbox | `vector vrl --print-object`, one process per line (runtime errors go to stderr without line alignment), empty environment, 20 s timeout, static denylist of host-reading functions (`get_env_var`, `get_hostname`, secrets, DNS). |
| I7 | Parser contract | The program receives `{message}` and assigns ECS fields on the root. At deployment it is wrapped: envelope saved, event reset (JSON round-trip so Vector's type checker sees an open object), `event.original` added, envelope rebuilt with `ecs` and `parser_id`. |
| I8 | Deployment | `vector/vector.yaml` = sources; `vector/pipeline.yaml` generated from approved parsers (route by source, one remap per parser, `drop_on_error` + `reroute_dropped` so failures return to quarantine). Every approval is checked with `vector validate`; a config Vector cannot load is rolled back. Vector runs with `--watch-config`. |
| I9 | Loop checks | In order: JSON answer, self-reported status (D38a), compile, runtime on every sample line, ECS validation (field sets, enumerations, IP and port types), grounding (D38b). Stagnation = same failure class twice in a row (D38c). A proposal is then re-run locally on the *real* lines (`real_lines_ok`) to prove that shape-preserving pseudonyms did not mislead the parser. |
| I10 | Leak guard | `LLMClient.chat` refuses to send any message containing an original value, whatever the provider. Only sizes, latency and token counts of calls are logged, never content. |
| I12 | First real run | On a consumer GPU the first run looked stuck. Fixes: live progress per attempt; preflight checks (Vector binary, LLM server, model name) before any LLM time; reasoning mode off by default for the local model (`/no_think` soft switch, `PRIVASOC_LLM_LOCAL_THINK`); only the latest attempt kept in context, since small local models have small windows. `init` now adds settings introduced after the `.env` was created. |
| I13 | Answer format | First real run with `qwen3:8b`: 3 of 5 attempts lost to invalid JSON, because VRL regexes (`\d`, `\S`) break JSON string escaping. Code is no longer requested inside JSON: the model answers `STATUS:` / `REASON:` lines plus a fenced ```` ```vrl ```` block (JSON still accepted). Truncated answers (`finish_reason=length`) get specific feedback. Prompt states that VRL has no methods (`split(x, ":")`, not `x.split(":")`), the second observed error. Sandbox output decoded as UTF-8 (Windows defaulted to cp1252, garbling compiler errors fed back to the model). |
| I14 | Second real run | (1) Answers still truncated at 2048 tokens: `/no_think` alone does not disable Qwen3 reasoning on Ollama's `/v1`; the local client now also sends `reasoning_effort: "none"` (retried without it if a server rejects the field). (2) **Residual leak found on real Pi-hole v6 logs**: hostnames under a private TLD (a private TLD) were not detected and reached the (local) model. Any lowercase multi-label name is now an FQDN candidate; path components and code namespaces are excluded. Regression test added. (3) The model twice used a variable without assigning it: feedback now carries hints per VRL error code and the numbered program; the system prompt has a complete worked example that is itself tested. (4) Stagnation now means the *same* error (codes or fields) twice, not just the same class. |
| I15 | Deterministic repairs | In structured mode the model repeated invalid categorisation values (`event.type: dns`, `event.outcome: blocked`) despite precise feedback. Such values are now removed automatically, never invented, and every repair is reported to the model and shown to the reviewer (`auto_repairs` metric). A prefix that swallows what the shapes expect gets a targeted hint (the shapes would match if the prefix kept only the timestamp). |
| I16 | Repairs and partial parsers | Replaying the three real structured runs of `qwen3:8b` showed the shapes were right every time and the failures came from the prefix and mappings. Deterministic, value-free repairs now apply before validation: unnamed prefix groups are named, the timestamp group is found by trying the stated format on each prefix group, a prefix that swallows what the shapes expect is cut back to the timestamp, mappings to missing groups or non-ECS fields are dropped, and constants outside categorisation fields (invented values such as `network.transport: udp`) are dropped. Each repair is reported. A spec that covers at least `PRIVASOC_MIN_COVERAGE` (0.8) of up to 500 real lines, measured locally, can be proposed as partial; unmatched lines keep going to quarantine. Retries raise the temperature (0.2 → 0.8) so the model does not resend the same answer. Result on the recorded real answers: 3 runs out of 3 that previously failed now give 1 full parser (100 % of recent lines, 0 ungrounded values) and 1 partial (89 %), the third still stagnates. |
| I17 | First real parser | `qwen3:8b`, structured mode, real Pi-hole v6 logs: proposal after 3 attempts, 28.5 s of LLM time, 6 automatic repairs, 10/10 sample lines parsed, 0 ungrounded values, 100 % of recent real lines covered. Human review then caught what automated checks did not: `dns.resolved_ip` received non-IP answers (`NODATA-IPv6`), and blocked/local answers were mapped to `destination.ip`. Fix: the compiler only assigns IP fields when the value is an IPv4/IPv6 (`is_ipv4`/`is_ipv6`), and `dns.resolved_ip` joins the validated IP fields. Semantic choices (which ECS field) remain the reviewer's job, which is the point of D23. |
| I18 | Held-out coverage | A real proposal passed 10/10 sample lines yet missed `cached x is NODATA-IPv6` on 25 % of recent lines: the value differs but the Drain template is the same, so stratified sampling cannot see it. A structured spec that passes the sample is now checked on up to 500 real lines of the source (local Python dry run). Up to five unmatched lines, chosen across templates and pseudonymised first (their originals join the leak check), are fed back as a `coverage` failure; the best spec above `PRIVASOC_MIN_COVERAGE` stays a partial candidate. The prompt also gives one-line meanings for the key ECS fields (e.g. `dns.resolved_ip` = IPs in a DNS answer), after two real runs put DNS answers in `destination.ip`. |
| I19 | Held-out feedback works | Next real run (`qwen3:8b`, structured): 5 attempts, 48.7 s of LLM time. After the held-out coverage feedback, the model added two shapes it had never seen in its sample (`cached x is NODATA-IPv6`, `special domain x is NXDOMAIN`) and mapped DNS answers to `dns.resolved_ip` and query types to `dns.question.type`. Result: partial parser covering 94 % of 500 real lines and 100 % of recent ones, 0 ungrounded values, 9 automatic repairs. Remaining gaps are visible to the reviewer (a malformed YAML mapping dropped `dns.resolved_ip` for `cached-stale`; `cached x is <IP>` still unmatched). |
| I20 | Leakage measured | Ground truth for sensitive values = what Elastic's pipelines extract (IPs, hosts, users, domains) on the 10 fixtures, counted only when the value appears literally in the raw line. Regex detectors of step 1: **26.8 %** of 2,010 values leaked (syslog header hosts 89 %, URL hosts 80 %, user names 33-70 %). Added from these measurements: syslog RFC 3164/5424 header host, user phrases (sshd, sudo, `user <x>`), `DOMAIN\\user`, Common Log Format ident/user/client, URL hosts, IPv6 behind an `iface:` prefix, IPv4 followed by a full stop, quoted key=value values and more vendor keys. Result: **8.1 %**. The remainder is mostly positional fields (e.g. the squid user column) and bare names without context; the local-LLM pass (step 5) and parser-aware pseudonymisation target them. Example leaked values are shown locally but never written to the report (they come from ELv2 data). |
| I21 | Evaluation protocol | Per fixture: first half of the lines visible to the generator (sampling and held-out coverage check), second half never shown and used for scoring. Micro F1 over extractable ECS fields (addresses, ports, users, hosts, process, DNS, URL/HTTP); vendor namespaces, enrichment, timestamps and categorisation are excluded. pass@1 = share of runs that propose a parser; pass@k = share of fixtures with at least one proposal in k runs. `--pseudo off` is an ablation for local models only (refused for remote providers in code). Results are appended to JSONL so runs resume. |
| I22 | Reference baseline | Hand-written specs (`evaluation/reference/`, 4 formats) run through the exact same pipeline as the models (`--providers reference`). They give the ceiling of the structured mode and tested the harness end to end, which found two bugs that would have penalised every model: the compiler's IP guard did not type-check on prefix groups (VRL E651), and grounding rejected timestamps converted to UTC from a `+0200` offset. Reference result: 4/4 proposed, mean F1 0.87, 91 % of held-out lines parsed. Scoring no longer counts `*.address` and `url.path` (copies of `*.ip` and `url.original` in Elastic's output). |
| I23 | Structure detection | Before the model is called, privasoc detects known headers (syslog RFC 3164/5424, ISO timestamp, Common Log Format) and key/value styles (`k=v`, `k:"v";`...) on the pseudonymised sample, and hands the model the prefix, timestamp format, kv delimiters and keys seen. A model prefix matching fewer lines than the detected header is replaced. New `kv` spec section compiles to `parse_key_value`. The model keeps the semantic part: which ECS field each key or group means. |
| I24 | Context window | **Root cause of many early hallucinations**: through Ollama's OpenAI-compatible endpoint the context window is the server default (4,096 tokens) and longer prompts are silently cut from the start, system prompt included; logged prompts of 17-24k characters came back as 4,095 tokens and the model invented formats (`FW: accept`, `\\d{8}`). privasoc now uses Ollama's native `/api/chat` when available, with `num_ctx` per request (default 8,192: `qwen3:8b` Q4 plus 8k context stays entirely in 8 GB of VRAM, measured; 10k spills to CPU), `think: false`, sample lines capped at 400 characters, and a warning whenever a prompt fills the window. |
| I25 | Fixes driven by the dev set | Running `qwen3:8b` on the 10 dev fixtures, then reading every failure, produced: the `kv` section and standard mappings for keys the model picked but did not map (`src: src` -> `source.ip`), IANA protocol numbers to names, the real ECS field list (vendored from elastic/ecs, Apache-2.0) with renaming of unique near misses (`http.method` -> `http.request.method`), cross-line propagation of pseudonyms (a host keyed in one line appeared bare in another: caught by the leak guard), leak-guard vocabulary (a user called `admin` vs the ECS value `admin`), optional header for key/value lines, `\s+` for padded columns, quoting of bare `@timestamp` values. Each has a regression test built from the model's own output. |
| I26 | Results (qwen3:8b, 8 GB GPU) | **Free-form VRL: 0/30 parsers** (compile and runtime errors). **Structured: pass@1 70 %, pass@3 80 %, F1 0.53 when proposed** on the dev set, **0 ungrounded values** in 90 runs. Pseudonymisation costs little: F1 0.53 with vs 0.57 without, pass@3 80 % vs 70 %. Hand-written reference: F1 0.87 (ceiling of the pipeline). **Holdout (4 formats never used for tuning): pass@1 67 %, F1 0.21 when proposed**: parser generation generalises, field mapping much less, which is the honest limit of an 8B model plus hand-made repairs. Hard cases: Cisco ASA/IOS (dozens of message types), squid (positional columns), composite values (`ip:port:zone`). |
| I27 | One line at a time? | Tested (qwen3:8b, first line of each of the 10 dev formats, 3 attempts): free-form VRL for a **single line** still fails 8/10 (compile and runtime errors: the limit is knowledge of VRL, not the size of the input). Structured spec for a single line: 6/10, the same level as with a 10-line sample (7/10), and it loses the other line shapes. Sources are already grouped by sender (`syslog:<ip>`, D26/I1), but one sender emits several shapes (Pi-hole 7, Cisco dozens), so "one IP = one format" does not hold. The promising part of the idea is template-by-template generation (one Drain template at a time, then merge), aimed at the many-shape formats where the current approach fails (Cisco ASA/IOS). |
| I28 | Onboarding implementation | New `hosts` table; lines of a pending host are stored as *held* quarantine rows, invisible to `propose` and to any model; a rejected host's held lines are deleted and its future lines dropped. Gating happens where lines are stored, so Vector only ever runs parsers of approved hosts. A file import (`privasoc import`) counts as the admin's decision and approves its host. Known formats = Vector built-ins that understand the whole line: `parse_apache_log` combined/common, `parse_nginx_log` combined, `parse_cef`, each with a fixed ECS mapping; a syslog header alone is not "known" (the body stays opaque) and goes to the LLM path. Backfill re-runs the approved parser in the sandbox on up to 5,000 quarantined lines and moves them to events, updating the health counters. Verified end to end with Vector hot reload: 20 held lines ingested on approval, then new lines parsed by Vector. |
| I29 | Health implementation | Per-minute counters per host (total, parsed, clock skew). Baseline over the observed window (up to 24 h). Silence: critical after max(10 min, 5 x usual gap); volume: warning below 20 % or above 5 x the baseline (after 60 active minutes; a fully silent host is the silence check's job); parse rate over 1 h: warning below 90 %, critical below 50 %; skew: warning above 300 s. Thresholds overridable per host (`privasoc hosts thresholds`). History stores status changes only. |
| I30 | UI implementation | Parser generation takes minutes on a small GPU, so the UI runs it as a background job (one at a time: one GPU) with its own SQLite connection, and the page polls the job's log. API and UI share one connection; writes go through a lock and blocking work runs in the thread pool, never on the event loop. A missing or broken Vector binary is reported as an error instead of a crash, and no longer marks the proposed parser as rejected (only Vector refusing the parser does). Verified in a browser (light, dark, phone width, no console error under the CSP) and by 11 tests: login, open-redirect guard, CSRF, headers, escaping, pseudonymised display, approve/reject, thresholds, background proposal against a fake LLM server. |

| I33 | Step 7 implemented and measured | The model gets the request, a catalogue of the fields present in the last 2,000 events (with pseudonymised examples) and one pseudonymised event per sender, and answers Sigma YAML; errors (invalid YAML, unknown field with close names, dict values, wrong correlation reference, unsupported modifier with the supported list) go back for up to 3 attempts. Backtests run the production engine in memory; base rules of a correlation are shown but raise nothing. A false-positive fix is compared with past alerts of the original rule (false positives removed, true positives kept or **hidden**); approving it disables every rule of the original file, disabling it restores them. Any rule can be switched off (`privasoc sigma disable`, `/ui/detection`). **Bench (`qwen3:8b`, 3 runs per case, ~3 s per request): dev 83 % exact answers (precision 0.85, recall 0.90), holdout 47 % exact (precision 0.57, recall 0.52), 97 % valid rules in both.** Dev tuning, done before the holdout run: a value_count example and actionable error texts, "no length modifier, use |re", "a correlation only when the question asks for a count" (took dev from 7/10 to 9/10 on the first run). Holdout failures, not tuned: exact values where a prefix or substring was needed (`url.path: wp-login.php`, `/admin` missing `/admin/users`), a negation written as `!10.x/8` then dropped, invented constraints (`event.outcome: failure` on WordPress logins), and a regex written on the **pseudonymised** shape of a domain (`d[0-9a-f]{6}\\.org`): pseudonymising public domain names such as pastebin.com costs detection quality, an open design question. **Three privacy bugs found by this step and fixed:** ECS fields were pseudonymised only through text detectors, so `"user":{"name":"bob"}` reached the model in clear (now pseudonymised by field meaning, also in triage); a document could be pseudonymised twice (an IP pseudonym is itself an IP), which broke re-identification; the leak guard blocked values that are part of our own fixed instructions (`10.0.0.0` in the example rule) or that the model wrote itself. |
